# CCTV build roadmap (from 2026-09-25)

Everything agreed on 2026-09-25, in build order. Each phase gets its own short spec (design) and a
detailed task plan before code, is built with tests, tried on the test server
(https://192.168.3.147:8443, now production), and only then does the next phase start.
Numbers in brackets are the feature numbers from the chat list.

Rules for every phase: nothing changes NVR/camera settings without the owner's OK; all features
are on/off settings; no server transcoding (encoding stays on the cameras); server footage is
admin-only until phase 6 adds per-user rights.

---

## Phase 0 — Housekeeping (owner actions + small fixes) · ~½ day

Owner: swap test PC Ethernet cable/port; find cause of the 08:30 restart (Windows Update
active hours / power); Windows Defender exclusions for the WSL disk and the USB recording drive;
DHCP reservations for NVRs and the test PC; SD streams to H.264 via Sites → Sub-streams; restart
PowerToys on the test PC; quit Docker Desktop on this PC.

Me (with OK): WSL memory limit; test-drive retention + delete ~65 GB old test footage; turn off
crash-debug tracing once proven; mark value4u + rigginglot remote. Fix the stuck
`NET_SDK_FindRecDate` call that made the watchdog restart the server (time budget + skip, not a
90 s hang).

## Phase 1 — Health alerts [1, 18, 21] · ~4 days

Spec: `docs/superpowers/specs/2026-09-25-health-alerts-design.md` (+ clock checks + backups).

1. `health.mjs` check engine: raise/clear rules, grouping, suppression, start grace.
2. Checks: server restart, drive missing/full, not-recording, camera/NVR offline, refusals,
   login failure, **NVR clock offset > 30 s** [18].
3. Delivery: ntfy + minimal SMTP client, retries, Test buttons, write-only secrets.
4. Health page, red banner, Settings → Alerts, `data/alerts.jsonl`.
5. Outside watcher in the test PC keep-alive (server down, Ubuntu down, drive gone, PC booted,
   ON/OFF pressed).
6. **Settings backups** [21]: nightly + before each deploy; settings, users, NVR list, prefs,
   recordings DB; to the recording drive and a Windows folder; `restore` command; shown on Health.

Done when: stopping cctv gives an ntfy within 3 min and "OK again" after; unplugging a camera
alerts once; backups appear nightly.

## Phase 2 — Playback redesign [5–11, 28, 30] · ~4 days

Mockup: scratchpad `mockup/cctv-mockup.html` (Playback tab).

1. New control bar layout (clock with ms, day arrows, zoom 24h/1h/10m + span slider [30]).
2. Two-lane timeline: server / from-NVR / gaps / motion lane.
3. Shuttle slider (spring-back, ¼×–16×, reverse = keyframes) on server playback.
4. Frame step ‹ › (`,` `.`): server sends single frames; paused-only.
5. Speed buttons; quality shows source ("HD · server" / "SD · NVR") + video badge.
6. Snapshot: current frame to JPEG (canvas), name = camera + time.
7. Tile status dots on live grid [28]: green = video arriving, red = recording.
8. Phone layout (controls wrap, transport first).
9. Seamless server → NVR handover: start the leg `legLeadMs` BEFORE the hole (not on reaching it)
   and hold its frames until the boundary ts; per-NVR lead from a measured EMA of leg start
   latency (p90 + 1 s, capped); keep both decoders alive across the join and swap on one frame;
   120 ms cross-fade to hide the HD→SD resolution change; one master clock (OSD never jumps);
   "filling from the NVR…" over the held frame if the leg is late; setting **skip gaps** (default
   on) for true gaps, < 1 s always skipped silently. Reverse and speeds > 8× keep today's jump
   (the NVR session cannot do them).
10. Timeline zoom: wheel/pinch zoom centred on the pointer, smooth 1 min – 7 days (24h/1h/10m
   buttons stay as presets), drag to pan, double-click to seek, adaptive tick labels
   (s/min/h/day), overview strip of the whole day with a draggable window, follow-playhead mode
   (off when panning, "⟲ follow" to resume), clip handles keep their times while zooming,
   `+` `−` `0` keys.

Done when: every control works on server and NVR playback, keyboard shortcuts work, phone width OK.

## Phase 2b — Gap backfill from the NVRs · ~2 days

Why: filling a hole live only works while the NVR still has it (~30 days) but the server keeps
6–12 months, so an unfilled hole becomes permanent. Backfill makes the hole go away for good and
removes the NVR from playback entirely.

1. Gap list from the recordings DB (recorder gaps + holes between segments), with reason and age.
2. Backfill job: for each gap younger than the NVR's own retention, ask the NVR for that stretch
   (rec-fallback `nvrCoverage`), pull it and write real segments + index at the right times.
3. Scheduling: off-peak window (setting, default 01:00–05:00), one camera at a time per NVR, rate
   limited, skipped while the NVR is refusing or busy, resumable, never competes with live
   recording or an export.
4. Marked in the DB as backfilled (source + when) so exports can state it; shown on the timeline
   in the server colour once filled.
5. Gaps that can no longer be filled (older than the NVR keeps, or the NVR has nothing) are marked
   permanent and stop being retried; listed on the Storage/Health page.
6. Live filling stays as the fallback for the last few hours, before backfill has run.

Done when: a hole made on purpose (stop recording for 5 min) is gone from the timeline the next
morning and plays from disk with no NVR call.

## Phase 3 — Bookmarks [19] · ~2 days

1. `bookmarks` table in recordings DB: camera(s), start/end, title, description, user, created.
2. Add from playback (button / `B`), edit, delete (admin or owner).
3. Diamonds on the timeline, list beside the video, search by text/date/camera.
4. Protected footage: housekeeping and thinning skip bookmarked stretches (+ margin).

## Phase 4 — Evidence export [2, 12–17, 18] · ~6 days

1. Clip selection: timeline handles, typed times, `[` `]` mark in/out.
2. Export dialog: several cameras, name, notes, optional password, burn-in time/name.
3. Formats: **evidence pack** (original segments + index + manifest with SHA-256 per file, signed
   with the server's Ed25519 key, notes, clock offset per NVR; single-file HTML player that
   verifies the signature and plays in the browser); **MP4** (remux, no re-encode; signed
   manifest alongside); **stills** (JPEG every N s from keyframes).
4. Encryption when a password is set (AES-GCM, key from password via scrypt).
5. Background job with progress in the header; **Exports page** (list, download, delete);
   warning for clips over 30 min.
6. Admin setting: allowed formats per role.
7. Export button on bookmarks and alarms.

Done when: an exported pack opens on another PC, verifies, plays; editing one byte fails
verification.

## Phase 5 — Storage page + thinning [3] · ~4 days

1. Storage page: each location, used/free, days kept per camera vs target, growth per day,
   "full in N days" forecast.
2. Time-lapse thinning job: after `fullDays`, keep keyframes only (1 per `timelapseS`), rewrite
   segments + index atomically; skip bookmarked/exported stretches.
3. Retention job honouring per-camera days and the free-space floor (oldest first).
4. Alerts integration (drive full forecast < 7 days).

## Phase 6 — Access, rights and audit [22, 17] · ~4 days

1. Per-user rights screen: live / playback server / playback NVR / export (formats) / admin,
   per camera or site.
2. Replace `canPlayServer` with the rights check everywhere.
3. Audit log: logins, failed logins, settings changes, exports, playback views; Audit page with
   filters; kept 1 year; included in evidence pack manifests (who exported).
4. Admin list shown on Health.

## Phase 7 — Events and Alarms page [20, 23] · ~6 days

1. Event intake from NVRs (motion, AI person/vehicle, offline) into the recordings DB.
2. Motion/AI-only recording modes use these events (pre/post seconds from settings).
3. Alarms page: prioritised list, filters, preview, acknowledge with note, open in playback,
   bookmark, export.
4. Alarm rules: camera + type + schedule → priority + notify (reuses phase 1 delivery).
5. Motion tuning view [23]: live motion overlay + activity meter vs NVR threshold (changing the
   NVR threshold needs OK per camera).

## Phase 8 — Multi-camera playback [25, 26, 27, 29] · ~6 days

1. Camera list with search + saved views (per user, like grid order).
2. 2×2 / 3×3 synced playback: one clock drives all tiles; server playback per tile.
3. Timeline lanes: "this camera" + "all cameras in view".
4. Tile toolbar: snapshot, copy, export (preselects that camera), maximise.
5. Export from a view = all its cameras.

## Phase 9 — Maps status [24] · ~1 day

Camera icons on the existing maps coloured by online / recording / alert; click → live/playback.

## Phase 10 — Later

Dell R540 production move (ZFS ~180 TB) · remote access (Tailscale or VPN) · PTZ · mobile view ·
P2P login once TVT sends SDK 1.3.2.
